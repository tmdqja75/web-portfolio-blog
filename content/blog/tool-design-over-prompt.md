## 프롬프트를 고치는 데 3주를 썼다

에이전트가 검색 도구를 엉뚱하게 호출하는 문제가 있었다. 우리는 시스템 프롬프트에 규칙을 더했다. 규칙이 열두 줄이 되었을 때도 호출 정확도는 그대로였다.

원인은 프롬프트가 아니라 도구 쪽에 있었다. 모델에게 준 스키마가 이랬다.

```json
{
  "name": "search",
  "parameters": {
    "query": { "type": "string" },
    "mode": { "type": "string" }
  }
}
```

`mode`가 무엇을 받는지는 프롬프트 어딘가에 적혀 있었다. 모델은 스키마를 보고 호출하고, 프롬프트는 읽다가 잊는다.

## 스키마가 곧 문서다

`mode`를 열거형으로 바꾸고 설명을 파라미터 옆에 붙였다. 프롬프트에서는 그 열두 줄을 지웠다.

```python
class SearchArgs(BaseModel):
    query: str = Field(description="사용자 질문을 그대로 넣는다. 요약하지 않는다.")
    mode: Literal["semantic", "keyword"] = Field(
        description="고유명사·코드·에러 메시지는 keyword, 그 외는 semantic."
    )
```

호출 정확도는 그 주에 올라갔다. 규칙을 모델이 읽는 위치로 옮긴 것 말고는 아무것도 하지 않았다.

## 도구는 적을수록 좋다

도구가 열한 개일 때 모델은 자주 비슷한 두 개를 헷갈렸다. `search_docs`와 `search_code`를 하나로 합치고 인자로 구분하게 하자 혼동이 사라졌다.

선택지가 줄면 실수도 줄어든다. 사람에게 주는 UI와 다르지 않다.

## 실패도 도구가 말해야 한다

빈 결과를 빈 배열로 돌려주면 모델은 같은 질의를 한 번 더 던진다. 대신 무엇을 시도했고 다음에 무엇을 바꿀 수 있는지 문자열로 돌려준다.

```python
if not hits:
    return "결과 없음. keyword 모드로 고유명사만 넣어 다시 시도할 것."
```

도구 반환값은 데이터가 아니라 다음 행동에 대한 지시다. 이걸 받아들이고 나서 프롬프트는 다시 짧아졌다.
